# Finder badges: Nimbus's own status decorations (#71)

Date: 2026-11-11
Status: approved scope, implemented in the #71 PR; live Finder check pending

## Scope

Decision (Jon, 2026-11-11): v1 ships two badges.

| Badge | Shown on | System badge image |
|---|---|---|
| **Failed to upload** | a file whose last upload attempt failed | `com.apple.icon-decoration.badge.warning` |
| **Kept downloaded** | an item pinned with Keep Downloaded (directly) | `com.apple.icon-decoration.badge.pinned` |

Out of scope: a "shared" badge. rclone's generic listing (`operations/list`)
carries no sharing state, so it would need a per-backend call per item.

## Declaring the badges

Decorations are declared in the extension's `Info.plist`, inside
`NSExtension`, under `NSFileProviderDecorations` (see
`FileProvider/NSFileProviderItemDecoration.h`). The `Info.plist` is
generated by XcodeGen, so the entries live in `project.yml` (target
`FileProviderExtension` → `info.properties.NSExtension`) and the generated
plist is committed alongside.

```yaml
NSFileProviderDecorations:
  - Identifier: app.casavargas.nimbus.FileProvider.uploadFailed
    BadgeImageType: com.apple.icon-decoration.badge.warning
    Category: Badge
    Label: Not Uploaded
  - Identifier: app.casavargas.nimbus.FileProvider.pinned
    BadgeImageType: com.apple.icon-decoration.badge.pinned
    Category: Badge
    Label: Kept Downloaded
```

Both images are system badges (declared in CoreTypes, conforming to
`com.apple.icon-decoration.badge`), so no assets ship. Finder shows only
the **first** `Badge`-category decoration an item returns, so the order
matters: a failed upload outranks the pin.

A unit test reads `project.yml` and the generated `Info.plist` and checks
that every identifier the code can return is declared in both.

## Which item property drives each badge

`FileProviderItem` conforms to `NSFileProviderItemDecorating`; its
`decorations` come from a pure helper in `Nimbus/Shared/ItemBadges.swift`:

```swift
ItemBadges.identifiers(pinned: Bool, uploadFailed: Bool) -> [String]
// uploadFailed first, then pinned
```

- **pinned** = `FileProviderItem.isPinned`: the item's own identifier is in
  `PinStore` for its cloud. Items kept downloaded only because a folder
  above them is pinned (`isKeptByFolder`) get no badge: the folder carries
  it, and badging every descendant would bury the one item the user acted
  on.
- **uploadFailed** = the item's identifier is in `UploadFailureStore` for
  its cloud (below).

The root container has no decorations.

## Where failed-upload state comes from

`UploadFailureStore` (`Nimbus/Shared/UploadFailureStore.swift`, compiled
into the app, the extension and visible to `NimbusTests`): one JSON file
per cloud in the app group, `UploadFailures/<cloud>.json`, holding a sorted
list of item identifiers. Same storage pattern as `PinStore`: coordinated
atomic writes, reads cached against the file's modification date. Being in
the app group, the state survives an extension or Mac restart.

Written by the extension:

| Event | Effect |
|---|---|
| `createItem`: the upload step throws | record the new item's identifier |
| `modifyItem`: the content upload throws | record `item.itemIdentifier` (the identifier the system knows) |
| `createItem` / `modifyItem`: the upload succeeds | clear the identifier (both the system's and the final one after a rename) |
| `modifyItem`: rename or move succeeds | move the record (and records under a moved folder) |
| `deleteItem` succeeds | drop the item and everything under it |
| cloud removed in the app (`CloudMonitor.remove`) | drop the cloud's file |

Not recorded: cancellations (`CancellationError`, `CocoaError.userCancelled`)
— the user or the system stopped the upload, it didn't fail. Failures in
the steps around the upload (mkdir, stat after upload, move) aren't upload
failures either and aren't recorded. `UploadFailurePolicy.shouldRecord(_:)`
holds that rule and is unit-tested.

## Reporting a change to the system

A replicated extension only gets asked for changes through the working set;
signalling any other container does nothing. Two parts:

1. **The item has to look changed.** The badge state is metadata, so it is
   folded into the item's `metadataVersion` (as the pin state already is).
   The failed flag adds a byte only while the upload has failed, so the
   version of every healthy item is byte-for-byte what it was before this
   change and existing domains see no churn. The content version is
   untouched, so nothing re-downloads and a pending local edit isn't
   treated as a conflict.
2. **The working set has to report it.** On a new failure the extension
   appends the identifier to `PinStore`'s change log (`markChanged`) and
   signals `.workingSet`. `WorkingSetEnumerator` already re-fetches each
   identifier in that log from the server and reports it with `didUpdate`,
   so the item comes back with its new decorations and metadata version.
   The log is now "items whose local-only state changed", not only pins;
   no anchor format change is needed.

A cleared failure needs no signal: it is cleared just before the
successful `createItem`/`modifyItem` completes, and the item handed back in
that completion already carries the cleared state.

### Limit: a brand-new file that never reached the server

When `createItem` fails for a new file, the system still tracks that file
under its own temporary identifier; Nimbus never handed it an item, so it
can't decorate it. The record is still written, but the working-set fetch
for it finds nothing on the server and skips it (the same path a pin on a
deleted item takes) — reporting it would create a phantom item. macOS's
own "waiting to upload" indicator covers that case. The failed-upload badge
therefore shows on files the system already knows from the server: edits
whose upload failed, and creates that left a file on the server.

## Tests (`NimbusTests`)

- `ItemBadges.identifiers` for all four (pinned, failed) combinations,
  including the order.
- `ItemBadges.metadataSuffix`: unchanged bytes for a healthy item, an extra
  byte for a failed one.
- `UploadFailureStore`: record/clear report whether anything changed,
  persistence across instances, per-cloud isolation, rename moves a
  subtree only, delete drops a subtree, `removeAll`.
- `UploadFailurePolicy.shouldRecord`: cancellations aren't failures.
- Declarations: every identifier is in `project.yml` and `Info.plist`
  with a `com.apple.icon-decoration.badge.*` image.

## Verification not automated

Install the build in `/Applications` and check in Finder:

- [ ] Keep Downloaded on a file shows the pin badge; Allow Removing
      Download removes it.
- [ ] Edit a file with the daemon stopped: the warning badge appears;
      restart the daemon and the badge clears once the upload succeeds.
- [ ] Badges survive quitting Nimbus and relaunching.
